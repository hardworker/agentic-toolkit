# Independent alternative recommendation

Reuse the existing job interface and worker route initially. Do not introduce a second queue solely for deduplication: `JobStore.enqueue_once` already keys jobs by `(tenant, request_key)`, and the existing tests confirm sequential reuse and tenant-scoped keys. Preserve this behavior while making acceptance durable and atomic in the production persistence layer. The fixture does not show that layer or an actual queue, so their mechanisms remain unknown.

The smallest credible extension is a customer-authorized submit/status/download interface around that job identity, retry-safe worker completion, a proper CSV encoder, and results retained for seven days from successful completion. Store a completion/expiry timestamp and enforce it on download and cleanup; changing `RESULT_TTL_HOURS` from 24 to 168 alone provides no enforcement. Keep idempotency-record expiry separate from result expiry and explicitly define what a retry after expiration returns.

**Strongest alternative:** a dedicated export queue with its own worker capacity. It enables independent concurrency limits and protects existing report latency when exports are large or bursty. Its cost is another dispatch, retry, and operational path; it does not itself make submission or completion idempotent. Prefer it if measured export duration, peak arrivals, queue age, or existing-report latency show that sharing workers misses an agreed service target. About 5,000 jobs/day is only 0.058 jobs/second on average; without job duration and burst measurements it cannot establish capacity. Measure representative export workloads and mixed-workload contention before choosing separate capacity.

Material assumptions and failure scenarios:

1. **Concurrent or restarted submissions can duplicate work.** The in-memory dictionary check/create is neither durable nor a demonstrated atomic transaction. Require a durable unique tenant/request identity and a recoverable link between job creation and worker dispatch, using the production system's existing mechanism where possible. Request-key semantics are unknown; bind the key to the request parameters and reject conflicting reuse, or define canonical equivalence if clients supply no stable key.
2. **Worker redelivery can corrupt status or publish inconsistent output.** `complete(job_id, result)` blindly overwrites state; retry and failure handling are absent. Finalize one successful result atomically for the job, make repeated completion harmless, and expose terminal failures to polling. Existing dispatch delivery guarantees are unknown.
3. **Knowing a job ID must not grant data access.** `get_for_tenant` rejects another tenant's job, but the HTTP layer and result storage are absent. Derive tenant identity from authentication and apply ownership checks to submission, polling, and downloads, including any object URLs. The existing lookup test alone cannot prove end-to-end isolation.
4. **Seven-day availability is currently unimplemented.** The only retention evidence is the unused 24-hour constant; there are no timestamps or cleanup behavior. Successful output must survive worker/process restarts, remain downloadable until expiry, and become unavailable afterward. Storage durability and download-link behavior are unknown.
5. **Ordinary customer data can produce invalid CSV.** `render_report` joins values without quoting commas, quotes, or newlines; the sole render test covers simple values. Use the standard CSV writer and verify these cases. Whether spreadsheet formula handling is required depends on the intended consumer and remains unspecified.

Validation evidence: `python3 -B -m unittest -v` passed all three existing tests. These establish only the fixture's sequential deduplication, tenant lookup behavior, and simple rendering, not concurrency, crash recovery, capacity, HTTP authorization, or retention.
