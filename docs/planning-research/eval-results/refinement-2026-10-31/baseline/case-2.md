# Keeping documentation current: comparison and pilot

Pilot **B, in-repository checks**, in one bounded documentation area, with the existing document owner reviewing the findings. Use **A, manual review**, as the comparison on the same changes. B offers a narrow, inspectable first question: can checks find valid link or public-interface problems that the owner would otherwise miss, at acceptable setup and review cost? It cannot establish that the documentation is semantically current.

The [four supplied descriptions](../../../eval-fixtures/planning-refinement.md#2-broad-documentation-comparison) are the only evidence. Existing capabilities below are **observed in those descriptions**, not tested here. Expected benefits and costs are **inferred**, and all performance claims remain **unknown**. The pilot must use existing infrastructure, introduce no hosted service, and publish nothing automatically.

These approaches address different parts of the job. A connects changes to meaning through owner knowledge. B checks a defined class of inconsistencies. C helps locate passages. D attempts the actual revision. All four still need a person who can determine whether a statement remains true. The descriptions provide no basis for ranking their factual accuracy or claiming time savings.

**The proposed pilot.** Choose one documentation area with an available owner, recent repository changes and examples relevant to B's narrow checks. Scope selection is a practical prerequisite; it does not require a new interview to decide the direction. Limit the first comparison to one weekly change window, and record if it contains too few relevant changes to be informative.

The flow is repository changes → change list and CI findings → owner assessment → proposed documentation updates → human approval. Existing CI and the reviewer workflow provide the operational boundary. Check findings must retain the change or link that prompted them so the owner can assess their basis. This plan leaves check design and implementation details to a separately authorized implementation phase.

For a fair initial comparison, have the owner record the manual assessment before seeing the check findings. Then assess the additional findings and corrections on the same change set. Separate setup time from recurring review and correction time. Record valid new problems found, false or unhelpful flags, meaningful issues the owner found that B missed, and whether ownership was clear. Direct inspection of the affected link or interface is evidence for an individual finding; agreement with the owner is not proof of exhaustive coverage.

The first pilot deliverable is a comparison of those observations and a small set of human-approved proposed updates, if any are warranted. Accept it as informative when each reported benefit or burden has a concrete example and the owner can distinguish B's coverage from semantic issues left to review. Retain B if it adds useful findings or reduces recurring effort without unacceptable review burden. Prefer A alone if it performs as well for this area with less total effort. If no relevant defect occurs, record an inconclusive comparison rather than claiming B is effective; a labeled, disposable example can check basic detection but cannot prove real-world value.

**Alternatives retained for the next decision.** A remains the fallback, not a failed option. C is deferred until evidence shows that finding affected passages is costly; that observation would justify comparing local retrieval against owner search. D is deferred until evidence shows that producing accurate text is a substantial bottleneck; it would need an explicit factual-error and reviewer-effort comparison before expansion. If the dominant misses are semantic, a successful link-check pilot still does not settle whether C, D or a better owner-review process should be tried next.

No additional hosted service or automatic publication is part of any pilot option. There are no user choices blocking this recommended scope; the owner, sample area and usable existing tooling must be verified when execution is authorized. Outcomes are **pending — no checks or performance comparison have run**.
